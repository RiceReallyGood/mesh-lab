## 2. 归因阶梯：加一个 sidecar 要多少钱

跨机三级，每级只多一个 sidecar，跨机 TCP 那一跳始终存在，所以**级差就是 sidecar 的净代价**。

- 参数：`c=1`、payload 64 B、每轮 20 s、5 % 采样、`ENVOY_CONCURRENCY=4`
- **3 轮 × 3 拓扑交错跑**（避免后跑的组白占缓存预热和 CPU 频率爬升的便宜）
- 样本：直连 20,669 / 单跳 19,911 / 双跳 13,396 条 trace，**九轮全部 0 失败**

### 2.1 各节点本地总时长

| 节点 | 直连 | 单跳 | 双跳 |
|---|---:|---:|---:|
| kitex-client | avg 139.9 / p50 **137.4** | avg 152.1 / p50 **145.9** | avg 230.9 / p50 **222.8** |
| envoy-out | — | avg 118.7 / p50 113.0 | avg 198.1 / p50 191.7 |
| envoy-in | — | — | avg 82.2 / p50 79.8 |
| kitex-server | avg 21.6 / p50 19.5 | avg 18.1 / p50 16.8 | avg 18.6 / p50 17.3 |

（单位 µs。参照值：client 147.3 / 163.2 / 228.2，server 23.2 / 21.3 / 17.7 —— 逐项对得上。）

### 2.2 「自身处理」与级差

自身处理 = 该节点总时长 − 它等待下一跳的时间。

| | 直连 | 单跳 | 双跳 |
|---|---:|---:|---:|
| client 自身 | **27.9** | **10.7** | **10.4** |
| envoy-out 自身 | — | **17.0** | **16.2** |
| envoy-in 自身 | — | — | **26.5** |
| **端到端 p50** | **137.4** | **145.9** | **222.8** |
| **级差** | — | **+8.5** | **+76.9** |

（p50，µs。参照的自身处理是 27.9 / 10.9 / 10.5 与 16.3 / 15.9 / 27.6 —— **几乎逐位相同**。）

**三个读法：**

**① `envoy-out` 自身在单跳和双跳里几乎不变（17.0 → 16.2 µs，差 4.7 %）。**
说明加第二跳不会让第一跳变慢，**sidecar 的代价是可加的**，容量规划可以线性外推。

**② 出向 sidecar 只要 +8.5 µs，因为它同时替客户端省了钱。**

| client 侧 | 直连 | 单跳 | 变化 |
|---|---:|---:|---|
| 写 socket | **6.5 µs** | **1.8 µs** | **−72 %**（跨机 TCP → 本机 UDS） |
| **goroutine 调度延迟** | **11.1 µs** | **2.8 µs** | **−75 %** |
| TTHeader 解码 | 3.1 µs | 0.71 µs | **−77 %** |
| **client 自身合计** | **27.9 µs** | **10.7 µs** | **−17.2 µs** |

直连时客户端自己在干重活：直接读写跨机 TCP socket、被网卡中断唤醒。
挂上本机 sidecar 后它只跟本机 UDS 打交道，这些成本转移给了 Envoy —— 而 Envoy 干同样的事只花 17 µs。

**③ 入向 sidecar 明显更贵：自身 26.5 µs vs 出向 16.2 µs（1.6 倍）**，
级差更是 +76.9 vs +8.5。参照报告归因于「是机器不是路径」（920B 单核性能更弱）。

## 3. 按机器分组的完整分解（双跳，低负载）

同机内的时间戳共用一个单调钟，**加减是精确的**；跨机只能得往返。
所以下面**把同机的 envoy 和 kitex 合在一起看**，正好也是分析上唯一站得住的切法。

用 **avg** 做这张表，因为**均值可加、分位数不可加**——各段之和精确等于端到端：

> 本节的端到端取 `detail` 口径的 **231.1 µs**，与 §2.1 表里 `summary` 口径的 230.9 µs
> 差 0.09 %。两者样本集略有出入（`detail` 按点位对齐，部分阶段 n=13,341 而非 13,396）。
> 差值不影响任何结论，但同一张表内必须用同一口径，否则不闭合。

```
                     suzhou950                                  suzhou920B
  ┌──────────────────────────────────────┐      ┌──────────────────────────────────────┐
  │ kitex-client 自身          11.4 µs   │      │ envoy-in 自身              29.1 µs   │
  │ client ↔ envoy-out  UDS往返 21.6 µs  │      │ envoy-in ↔ server  UDS往返 34.5 µs   │
  │ envoy-out 自身             18.9 µs   │      │ kitex-server 总           18.6 µs    │
  ├──────────────────────────────────────┤      ├──────────────────────────────────────┤
  │ 950 侧合计                 51.9 µs   │      │ 920B 侧合计                82.2 µs   │
  └──────────────────────────────────────┘      └──────────────────────────────────────┘
                     └──────── 跨机 TCP 往返  97.0 µs ────────┘

                        端到端 = 51.9 + 97.0 + 82.2 = 231.1 µs  ✅ 精确闭合
```

| 归属 | 段 | avg (µs) | 占端到端 |
|---|---|---:|---:|
| **suzhou950** | kitex-client 自身 | 11.4 | 4.9 % |
| | client ↔ envoy-out 机内 UDS 往返 | 21.6 | 9.3 % |
| | envoy-out 自身 | 18.9 | 8.2 % |
| | **小计** | **51.9** | **22.5 %** |
| **跨机** | envoy-out ↔ envoy-in TCP 往返 | **97.0** | **42.0 %** |
| **suzhou920B** | envoy-in 自身 | 29.1 | 12.6 % |
| | envoy-in ↔ server 机内 UDS 往返 | 34.5 | 14.9 % |
| | kitex-server 总（含业务 handler 0.26） | 18.6 | 8.0 % |
| | **小计** | **82.2** | **35.6 %** |
| | **端到端** | **231.1** | 100 % |

**这张表的三个结论：**

1. **两跳 sidecar 自身处理 = 18.9 + 29.1 = 48.0 µs，占端到端 20.8 %。**
   p50 口径是 42.7 / 222.8 = **19.2 %**。两个口径都落在 19 %–21 % 的合格区间。
2. **真正的大头是「在路上」的时间：跨机 97.0 µs（42 %）+ 两段机内 UDS 56.1 µs（24 %）
   = 66 %。** 也就是说三分之二的时间花在进程间/机器间传递，不是花在任何人的处理逻辑上。
3. **业务逻辑 260 ns，占 0.11 %。** 端到端 231 µs 里，真正干活的部分不到千分之二。

## 4. 高负载下的对比：涨的全是排队

同一套代码、同一条链路，只把负载从 1 并发提到 64 并发（40 秒，5 % 采样，
**213.6 万请求 0 失败，53,409 QPS**，采样 106,790 条 trace / 1.9 GB）：

| p50 | 低负载(c=1) | 高负载(c=64) | 倍数 |
|---|---:|---:|---:|
| 端到端 | 222.8 µs | **1.107 ms** | 5.0× |
| envoy-out 自身 | 16.2 µs | 24.2 µs | 1.5× |
| envoy-in 自身 | 26.5 µs | 31.4 µs | 1.2× |
| **业务 handler** | **230 ns** | **250 ns** | **1.0×** |
| **envoy-out 事件循环排队** | **130 ns** | **940 ns** | 7× |
| **envoy-in 事件循环排队** | **280 ns** | **22.7 µs** | **81×** |
| client goroutine 调度延迟 | 2.8 µs | 5.9 µs | 2.1× |

> **这张表是跨参数对比，不是严格对照实验**：低负载那列 payload 64 B（阶梯），
> 高负载那列 128 B（压测轮）。payload 差一倍会影响编解码和 socket 那几段的绝对值，
> 但改变不了「处理段不变、排队段暴涨」这个量级差异 —— 排队涨了 81 倍，
> 不是 payload 能解释的。要做严格对照得固定 payload 再跑一轮。

**一句话读法**：端到端涨了 5 倍，但**没有任何一段「处理」变慢** ——
Envoy 的解析、路由、编码，Kitex 的编解码，业务 handler，全都纹丝不动。涨的全是**排队**。

不插桩你只能看到「压力上来延迟从 223 µs 涨到 1.1 ms」，然后开始猜是不是 Envoy 慢了、
要不要换个代理。插了桩才能确定：**代理一点没变慢，是请求在等 worker。**
前者要换软件，后者只要加 worker —— 处理方式完全不同。

## 5. avg 列：这次新加的，以及为什么值得加

原来 `summary` / `detail` 只有 p50/p90/p99。本次给两个格式都加上了 **avg**
（`table` 格式本来就有 `__avg__` 行，只是主力格式没用上）。

加完立刻看出两件靠分位数看不见的事：

| 点位 | p50 | avg | 说明 |
|---|---:|---:|---|
| kitex-client「取连接」 | **230 ns** | **6.8 µs** | 只有首次请求要建连，被 p50 完全掩盖 |
| envoy-out「事件循环排队」（高负载） | **940 ns** | **15.9 µs** | 绝大多数请求不排队，少数排很久 |

**更实质的理由是：均值可加，分位数不可加。**
各段 p50 之和 ≠ 端到端 p50，所以 §3 那种「各段占比、加起来等于 100 %」的分解，
**数学上只有用 avg 才成立**——实测也精确闭合（51.9 + 97.0 + 82.2 = 231.1）。
代码注释里写清楚了这一点，`detail` 的跨节点分解现在同时给 avg 和 p50 两列。

## 6. 本次发现并修复的 bug：打点数据静默丢失

**症状**：同机直连跑 300 请求全部成功，`trace-server.ndjson` 却是 **0 条**。
单跳/双跳同样 300 请求却有 5901 条，看起来毫无规律。

**根因**在 `demo/probe/tracer.go`：落盘只有两个触发条件 ——
**1 MB 缓冲写满**，或**每秒的 Ticker**。300 请求 18 毫秒跑完、只产生约 380 KB，
两个条件一个都没触发，数据全在内存里。而压测轮跑几十秒、几十万条事件，缓冲被反复写满
一直在落盘，**所以这个问题在大压测里永远看不到**。

实测（同一份 300 请求的直连验证轮）：

| 停止方式 | server 落盘 | `[probe]` 统计行 |
|---|---:|---|
| 跑完立刻 `tmux kill-session`（旧脚本） | **0 条** | 无 |
| 跑完立刻 `pkill -TERM` | 346 / 1087 条（每次不一样） | 无 |
| **跑完等 1 秒再停** | **6300 条 = 应有的全部** | **有，`丢弃=0`** ✅ |

两个杀法各自的问题：SIGHUP（`tmux kill-session` 拆 pane 发的就是它）server 根本不处理，
默认动作直接终止；SIGTERM 虽然有处理器，但 `tr.Close()` 要 `close(ch)` + `wg.Wait()`
等 writer 排空并 flush，紧跟压测发信号时会和退出竞争。

**修复**：四个 `run-*.sh` 的 `stop()` 改成三步 —— `sleep 2`（让 Ticker 触发）→ SIGTERM →
最后拆 tmux。修复后同机三级全部拿到完整的 6300 条、`丢弃=0`
（**单跳原先的 5901 也是残缺的**，只是丢得少没被发现）。

**完整性判据**：`server.log` 里必须有 `[probe] node=… 总请求=N 采样=N 丢弃=0`。
**这一行不在就说明 `Close()` 没跑完，数据不可信**——比数行数可靠得多。

> **对本报告结论的影响：无。** 归因阶梯与压测轮用的都是 20–40 秒的大样本，
> 一直在正常落盘；受影响的只有几百请求的同机验证轮，而那一级只用来判断链路通不通。

## 7. 复现过程中的其它观察

**① `rust` 那项网络自检会假报不及格。** runbook §3.1 用
`channel-rust-stable.toml` 测 static.rust-lang.org，但那个文件只有 826 KB，
`-r 0-20000000` 取不满，测出来是握手延迟不是吞吐（本次 0.58 MB/s，参照 0.47 MB/s，
**都低于它自己写的 1 MB/s 及格线**）。换真实产物（`rust-std-*.tar.gz`）复测是 **6.80 MB/s**。
—— 建议 runbook 换个大文件做这项。

**② 构建中段会出现一次「看起来卡死」。** 日志停在
`Analyzing: 173 packages loaded`、load 掉到 1.0、编译进程只有 1 个，持续几分钟。
不是卡住 —— 是在解压 LLVM 工具链（`LLVM-22.1.8-Linux-ARM64.tar.xz`，1.77 GB），
**xz 解压是单线程的**。判据是 `bazel_out` 仍在以 ~800 MB/15 s 增长。

**③ `pkill -f <pattern>` 会杀掉刚启动的同名后台任务。** 这是 runbook 排错表里已记的坑，
本次又踩了一次：`pkill -f watch-build.sh` 把紧接着启动的新轮询器一起杀了（退出码 144），
因为启动它的那条 `bash -c` 命令行里也含这个字符串。**一律用 `pkill -x <进程名>`。**

**④ 两机时钟差 −14.78 秒**（参照 −15.47 秒），NTP 仍未启用。
分析对此免疫（已验证），只影响 waterfall 的视觉呈现。
