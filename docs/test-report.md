## 0. 一页结论

在**真实跨机**的双跳 sidecar 链路上,单次 echo 调用端到端 **206.0 µs**(p50),构成如下:

| 环节 | p50 | 占比 |
|---|---:|---:|
| **跨机网络往返** | **87.6 µs** | **42.5 %** |
| envoy-in 自身处理 | 25.8 µs | 12.5 % |
| envoy-in ↔ server UDS 往返 | 25.0 µs | 12.1 % |
| client ↔ envoy-out UDS 往返 | 21.9 µs | 10.6 % |
| envoy-out 自身处理 | 15.7 µs | 7.6 % |
| kitex-server 自身处理 | 15.3 µs | 7.4 % |
| kitex-client 自身处理 | 4.8 µs | 2.3 % |

三条主要结论:

1. **两跳 sidecar 自身处理合计 41.5 µs,占端到端 20.1 %。** 其中编码是主要成本,写 socket 几乎可忽略(270 ns)。
2. **进程间传输(两段 UDS + 一段跨机 TCP)合计 134.5 µs,占 65.3 %** —— 是 sidecar 处理成本的 3.2 倍。**双跳架构的代价主要在"多了两次进程间传输",而不是"Envoy 处理得慢"。**
3. **业务 handler 仅 240 ns。** 本次测量的几乎全部是框架与传输开销,没有业务噪声混入。

> **重要限制**:上表各项为 p50 的分解,而**分位数不可加** —— 各项 p50 之和(196.1 µs)与端到端 p50(206.0 µs)相差约 10 µs 属正常。该表用于判断**量级与占比**,不可当作精确的加法分解。

## 2. 方法论前提

### 2.1 归因必须在非饱和区进行

饱和后排队延迟主导端到端时间,waterfall 上"时间花在哪"会退化成"在队列里等",对归因无意义。因此先做 QPS 扫描定位拐点。

**QPS 扫描结果**(trace 关闭):

| 并发 | QPS | p50 | p99 | 相对上一档 |
|---:|---:|---:|---:|---:|
| 1 | 4,623 | 213 µs | 257 µs | — |
| 2 | 9,004 | 215 µs | 285 µs | ×1.95 |
| 4 | 14,920 | 257 µs | 435 µs | ×1.66 |
| 8 | 24,979 | 313 µs | 484 µs | ×1.67 |
| **16** | **43,231** | 353 µs | 795 µs | ×1.73 |
| 32 | 59,810 | 483 µs | 1.547 ms | ×1.38 |
| **64** | **83,951** | 638 µs | 2.387 ms | ×1.40 ← 拐点 |
| 128 | **78,037 ↓** | 1.324 ms | 5.498 ms | **×0.93** |

**QPS_max ≈ 84 k(c=64)。** c=128 时吞吐**倒退**、延迟翻倍,是典型的过饱和。

**归因测量固定在 c=16(≈43 k QPS,约 51 % 饱和点)**,该档 QPS 仍随并发近线性增长。

### 2.2 时钟:跨机绝对时间戳不可相减

本环境两机时钟相差 **16.18 秒**。若直接相减两侧 wall clock:

```
client wall = 1786006859211031460
server wall = 1786006842910103066
直接相减    = −16300 ms   → "server 比 client 早 16.3 秒完成"
```

**采用的方法**:每个节点用**自己的单调钟**测量本地区间,跨节点只做"两个本地时长相减",偏斜天然抵消(设计文档 §8.2.3)。同一批数据用差值法得出 **225 µs**,合理。

**鲁棒性验证**(三种条件下每个统计量**逐位相同**):

| 条件 | 链路开销 p50 |
|---|---:|
| 无偏移 | 302.6 µs |
| 人工注入 +50 ms | 302.6 µs |
| 人工注入 −16340 ms | 302.6 µs |

**根本限制**:差值法只能得到**往返总和,无法拆分单向**。要拆需 PTP + 硬件时间戳网卡。报告中所有跨机数字均标注为"往返"。

### 2.3 噪声下限

单次运行的噪声可超过待测效应。首轮四组对照曾出现"**加插桩反而快 4.9 %**"——物理上不可能,是**顺序偏倚**(固定顺序 基线→A→B→C,使靠后的组受益于预热)。

**修正**:改为**按轮次交错**(每轮内跑完四组,共 6 轮),并规定:

> 若某组的 [最小, 最大] 区间与基线区间重叠,**不得宣称存在开销**,只能说"低于本方法的噪声下限"。

实测整机轮间波动约 **3 %**。

## 3. 端到端时延分解

**样本数 25,542 条 trace,c=16,跨机双跳,payload 64 B。**

### 3.1 kitex-client(总 206.0 µs)

| 阶段 | p50 | p90 | p99 |
|---|---:|---:|---:|
| 取连接(连接池) | 240 ns | 320 ns | 930 ns |
| TTHeader 编码 | 80 ns | 90 ns | 120 ns |
| 编码(发送前) | 1.3 µs | 1.7 µs | 3.6 µs |
| 写 socket | 1.8 µs | 2.3 µs | 5.3 µs |
| **★等待对端(纯网络)** | **195.9 µs** | 241.6 µs | 484.4 µs |
| TTHeader 解码 | 690 ns | 1.4 µs | 3.5 µs |
| payload 解码 | 290 ns | 400 ns | 930 ns |

**client 侧 95 % 的时间在等对端。** 自身处理仅约 4.8 µs。

> 这个结论此前看不到:Kitex 预定义的 `ReadStart` 记录于 `Read()` 入口,那时尚未开始读,真正的阻塞埋在 `codec.Decode` 内部,于是 `read_start→read_finish`(199.0 µs)吞掉了整个网络等待。补上 `mesh_socket_read_start` / `mesh_first_byte` 后才分得开。

### 3.2 envoy-out(总 174.0 µs)

| 阶段 | p50 | p90 | p99 |
|---|---:|---:|---:|
| ①→② TTHeader 解析 | 3.2 µs | 3.7 µs | 7.0 µs |
| ②→③ 协议层解头 | 510 ns | 600 ns | 1.1 µs |
| ③→④ 路由匹配 | 530 ns | 690 ns | 1.3 µs |
| ④→ 取上游连接 | 1.9 µs | 2.2 µs | 9.3 µs |
| 　编码 | **4.9 µs** | 5.4 µs | 9.4 µs |
| 　写 socket | **270 ns** | 330 ns | 680 ns |
| **⑤→⑥ ★等待上游** | **156.3 µs** | 197.4 µs | 409.3 µs |
| ⑥→⑦ 响应解码 | 4.4 µs | 4.9 µs | 8.0 µs |

**自身处理合计 ≈ 15.7 µs,等待上游占 90 %。**

### 3.3 envoy-in(总 68.7 µs)

| 阶段 | p50 | p90 | p99 |
|---|---:|---:|---:|
| ①→② TTHeader 解析 | 4.7 µs | 5.3 µs | 8.0 µs |
| ②→③ 协议层解头 | 951 ns | 1.1 µs | 1.4 µs |
| ③→④ 路由匹配 | 1.0 µs | 1.2 µs | 2.2 µs |
| ④→ 取上游连接 | 4.1 µs | 5.0 µs | 12.4 µs |
| 　编码 | **7.4 µs** | 8.1 µs | 12.2 µs |
| 　写 socket | 690 ns | 820 ns | 1.0 µs |
| **⑤→⑥ ★等待上游** | **40.3 µs** | 61.3 µs | 172.9 µs |
| ⑥→⑦ 响应解码 | 7.0 µs | 7.6 µs | 10.2 µs |

**自身处理合计 ≈ 25.8 µs**,是 envoy-out(15.7 µs)的 1.6 倍。**两跳不对称**,与 160 核 vs 384 核的硬件差距一致 —— 做容量规划时不能假设两跳成本相同。

### 3.4 kitex-server(总 15.3 µs)

| 阶段 | p50 | p90 | p99 |
|---|---:|---:|---:|
| epoll 唤醒 → 开始读 | 990 ns | 1.8 µs | 2.5 µs |
| ★等待对端(纯网络) | **320 ns** | 590 ns | 720 ns |
| TTHeader 解码 | 1.9 µs | 3.4 µs | 12.4 µs |
| payload 解码 | 490 ns | 580 ns | 860 ns |
| ★等待请求体 | 560 ns | 710 ns | 2.6 µs |
| **业务 handler** | **240 ns** | 320 ns | 500 ns |
| TTHeader 编码 | 100 ns | 110 ns | 150 ns |
| 编码(发送前) | 1.7 µs | 2.0 µs | 2.9 µs |
| 写 socket | **2.9 µs** | 5.6 µs | 6.9 µs |

**一个反直觉的读数**:server 被 epoll 唤醒后,"等待对端"仅 **320 ns** —— 说明**唤醒时数据早已在内核缓冲区**,`Peek` 直接命中,并未真正阻塞。真正的成本在"唤醒本身"(990 ns)与"写 socket"(2.9 µs)。

### 3.5 跨节点分层分解

四个节点的本地总时长构成嵌套关系:

```
client 总 206.0
  ├─ client 自身                          4.8
  ├─ [client ↔ envoy-out UDS 往返]        21.9
  └─ envoy-out 总 174.0
       ├─ envoy-out 自身                  15.7
       ├─ [跨机网络往返]                   87.6
       └─ envoy-in 总 68.7
            ├─ envoy-in 自身              25.8
            ├─ [envoy-in ↔ server UDS 往返] 25.0
            └─ server 总 15.3
```

由差值法直接测得(单位 µs):

| 差值 | 数值 | 跨机? |
|---|---:|---|
| client 总 − envoy-out 总 | 32.0 | 同机,精确 |
| envoy-out 总 − envoy-in 总 | 105.3 | **跨机 → 往返,不可拆单向** |
| envoy-in 总 − server 总 | 53.4 | 同机,精确 |

## 4. 打点自身的开销

四组对照,c=16,**6 轮交错**,每组取中位数与 [最小, 最大]。

| 组 | 优化前 | 优化后 | 判读 |
|---|---:|---:|---|
| 基线(探针未激活) | — | — | |
| A 探针激活 / 采样 0 | −1.5 % | +2.4 % | **区间与基线重叠 → 低于噪声下限** |
| B 探针激活 / 采样 1 % | −2.7 % | +0.9 % | **区间与基线重叠 → 低于噪声下限** |
| **C 探针激活 / 采样 100 %** | **−8.4 %** | **−6.6 %** | **区间分离 → 效应可辨** |

**结论:**

1. **按实际归因配置(1 % 采样)使用时,打点开销测不出来** —— 低于本方法约 3 % 的噪声下限。
2. **100 % 采样的开销明确可测(−6.6 %),不适合压测场景。** 这从实证角度印证了采样机制的必要性,而非过度设计。
3. 三项优化使 C 组开销降低 **1.8 个百分点**。

> **两轮基线本身相差 2.9 %**(42,772 vs 41,526),因此**不可跨轮比较绝对 QPS**,只能比较"相对基线的百分比"。

### 已做的三项优化

| 优化 | 消除了什么 |
|---|---|
| trace-id 改为共享指针,point 名改 `string_view` | **每个事件一次堆分配**(32 字符 trace-id 超过 SSO 阈值),8 点 = 8 次/请求 |
| `rpcEvent` 只读单调钟,wall 由基准点推算 | **每个事件一次 `clock_gettime`**,8 点 = 8 次 vDSO/请求 |
| `endRpc` 不再落盘,改由线程退出兜底 | **每个采样请求一次 write 系统调用** |

**未采样请求**的代价始终是"一次 enabled 判断 + 一次哈希查找 + 一次布尔判断"。

## 6. 局限与未决问题

### 6.1 测量方法的局限

| 局限 | 影响 |
|---|---|
| **分位数不可加** | §0 的占比表用于判断量级,不可当作精确加法分解 |
| **噪声下限约 3 %** | 小于此的效应(如 1 % 采样的开销)无法分辨 |
| **跨机只能得往返** | 无法拆分去程/回程,需 PTP + 硬件时间戳网卡 |
| **最后一批 trace 可能滞留** | 流量停止后不足一个刷盘间隔(200 ms / 512 条)的事件留在内存;对数万样本的统计无影响 |

### 6.2 尚未覆盖的点位

| 缺口 | 价值 | 障碍 |
|---|---|---|
| **netpoll 内部**(epoll_wait 返回 → OnRead 回调) | Go 侧写 socket 比 Envoy 贵 7–10 倍,原因需进一步分辨 | 需修改 netpoll 仓库 |
| 中间件链开销 | 预计 1 µs 量级 | 未实现 |
| listener accept | 连接级而非请求级 | 已由 `client_conn_*` 与 `up_conn_new` 间接覆盖 |

**一个待解释的现象**:

| 写 socket | p50 |
|---|---:|
| envoy-out (C++) | 270 ns |
| kitex-client (Go) | 1.8 µs |
| kitex-server (Go) | 2.9 µs |

**Go 侧比 Envoy 贵 7–10 倍。** 这里混着 netpoll 的缓冲管理与 goroutine 调度,不全是 syscall 本身。要分辨需深入 netpoll。

### 6.3 环境相关

- suzhou950 **未启用 NTP**,两机时钟差 16.18 s。分析对此免疫,但合并后的 waterfall 在**视觉上**会呈现"响应早于请求"。建议启用 NTP(仅需毫秒级)。
- 两机 CPU 规格不同(384 vs 160 核),**两跳成本不对称**,容量规划时需注意。
